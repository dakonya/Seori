# DetectionCI v0.1 — запуск и текущий результат

Это первая реализованная версия проекта. Контроллер написан на Python, данные хранятся в SQLite. Веб-интерфейс работает без npm, CDN и сторонних JavaScript-библиотек. Для локальных проверок нужен Python 3.11+ под Linux/macOS; под Windows используется WSL2.

## Быстрый запуск

Открой терминал в корневом каталоге проекта после клонирования.

```bash
python3 -m detectionci verify-fixtures
python3 -m detectionci suite --mode fixture --output reports
python3 -m detectionci serve
```

После последней команды открой http://127.0.0.1:8787. Сервис работает, пока открыт терминал; Ctrl+C завершает его с отменой активного задания и ограниченным по времени ожиданием очистки.

Если проект скачан как ZIP, сначала распакуй его и перейди в получившуюся папку `DetectionCI`. Установка пакетов для этих команд не нужна.

## Что уже реализовано

- Каталог сценариев, строгая проверка их структуры и ожидаемых результатов.
- Долговечная очередь запусков в SQLite, отмена и восстановление после прерывания контроллера.
- Три режима: локальные тестовые данные, replay через Wazuh logtest, ограниченный live через SSH.
- Привязка оповещения к агенту, файлу и временному окну; защита от старых и повторно посчитанных событий.
- Проверяемая очистка и сохраняемая блокировка стенда, состояние которого не подтверждено.
- JSON/HTML-отчёты, редактирование известных секретов и хеши сохраняемых доказательств.
- Неизменяемые baseline-снимки и сравнение повторных запусков.
- Веб-интерфейс, HTTP API, тесты и GitHub Actions для локальных проверок проекта.

В каталоге есть 12 штатных сценариев. Три из них поддерживают live-проверку создания, изменения и удаления файла в выделенном каталоге VM; три содержат SSH-логи для replay. Остальные проверяют логику сопоставления и обычные контрольные случаи на тестовых данных.

Отдельные четыре сценария намеренно получают FAIL либо INCONCLUSIVE. Команда `verify-fixtures` проверяет, что их фактический вывод соответствует ожидаемому. Эти случаи не смешиваются с обычным набором, который должен пройти успешно.

## Что означают результаты

| Режим | Что реально проверяется |
| --- | --- |
| Fixture | Логика программы на заранее заданных синтетических событиях |
| Replay | Правила и декодеры настоящего Wazuh на переданных записях |
| Live | Разрешённое действие в лабораторной VM и его наблюдаемый путь до оповещения |

Fixture PASS не доказывает обнаружение атаки настоящей SIEM. Программа не подставляет тестовые события при недоступности Wazuh. ERROR, FAIL, INCONCLUSIVE и CANCELLED возвращают неуспешный результат проверки.

## Проверка настоящего Wazuh

Подробная инструкция находится в [lab/README.md](lab/README.md). Она содержит подготовку официальной версии Wazuh, XML-правила, настройки мониторинга файлов и пример конфигурации клиента.

Для live нужны отдельная Linux VM с Wazuh-агентом, проверенный SSH host key, доступ к API и корректные TLS-сертификаты. Проверка состояния файла не называется проверкой получения исходного журнала менеджером: ненаблюдаемые промежуточные этапы не заявляются.

После аварии либо неподтверждённой очистки последующие live-запуски блокируются. Команда `target status` показывает причину. Сброс разрешён только при остановленном worker:

```bash
python3 -m detectionci target status
# Сначала независимо восстанови тестовую VM.
python3 -m detectionci target reset --acknowledge-restored
```

Сброс подтверждает выполненное оператором восстановление; он не восстанавливает VM самостоятельно. Контроллер слушает только loopback. Для доступа с другой машины используется SSH-туннель.

## Фактическая проверка этой версии

Итог автоматических тестов сохранён в [docs/verification-results.json](docs/verification-results.json). Область и ограничения проверок описаны в [docs/verification.md](docs/verification.md).

В среде сборки отсутствуют Docker и установленный Wazuh, запрещено открытие сетевого listening socket. Поэтому настоящие replay/live, запуск HTTP-сервера и браузерное отображение здесь не подтверждены. API проверяется через настоящий HTTP-парсер на соединении в памяти; SSH-helper дополнительно выполняется на временных файлах без подключения к машине пользователя.

Для демонстрации работодателю следующим проверяемым рубежом будет первый реальный live-запуск и воспроизведение поломки детекта с отчётами до и после исправления.
